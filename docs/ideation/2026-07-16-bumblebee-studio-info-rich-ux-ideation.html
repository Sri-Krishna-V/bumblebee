Grounding Context

Codebase Context. Bumblebee Studio is the Reflex web frontend (web/bumblebee_studio/) over the bumblebee Python pipeline (src/bumblebee/). Today the studio shows: a drag-drop PDF upload, a static "layout → OCR → chunks" spinner, and results as two tabs — Chunks (kind, section breadcrumb, pages, token estimate, text truncated at 1,200 chars) and Markdown (80k-char preview) — plus a five-tile stats row (pages, regions, OCR regions, chunks, parse time).

The central finding: the pipeline already computes far more information than the UI shows, and most of it is dropped at exactly one or two seams. Per-region OCR confidence (0–1 from token logprobs) is stripped by sanitize_layout_json() (src/bumblebee/stats.py:19) one call before the API responds. Normalized 0–1000 bounding boxes ship to the client inside every chunk record and are never rendered. A 7-stage timing model with queue/exec splits (DocumentTimings), per-region latency and token counts, adaptive-retry bookkeeping (regions below 0.80 confidence re-OCR'd at 2× DPI), and a 25-class layout-label vocabulary all exist server-side and reach no user.

External context. Best-in-class tools converge on the same patterns: per-word/ per-block confidence with threshold routing (Azure Document Intelligence, AWS Textract's three-tier auto-pass / spot-check / manual review), paragraph-level boxes with typed blocks (Mistral OCR 4), hover-synced source↔output panes with a live cost footer (the run-llama "baby-llamaParse" playground reference), and toggle-on confidence heatmaps (Sonix transcripts). Recurring practitioner complaint: document-level confidence is misleading because failures are local.

Product context. Solo developer, faculty-demo goal, $30 Modal compute budget, private-until-benchmarks. Ideas were weighted toward high information density per unit of engineering cost, and away from backend rearchitecture.

1

Trust Lens — confidence heatmap + review queue

confidence-quality Conf 90% Cx Medium
Description
Stop stripping _ocr_confidence at the API boundary (opt-in flag or default), then make quality visible in two layers: a heatmap toggle that tints each chunk card (and eventually each markdown block) by confidence, and a review queue — a filterable "needs review" list of regions that fell below the existing 0.80 threshold, annotated with the adaptive-retry story the pipeline already lives ("23 regions OCR'd · 3 flagged · re-OCR'd at 2× DPI · 2 improved 0.71 → 0.94"). Tier badges follow the industry-standard three-tier routing: auto-pass / spot-check / review.
Basis
direct: src/bumblebee/stats.py:19 — PRIVATE_JSON_KEYS = frozenset({"_ocr_usage", "_ocr_latency_ms", "_ocr_status_code", "_ocr_confidence"}), applied via sanitize_layout_json() at the single api.py call site; confidence is computed to 4 decimals (format.py:503-504) and deleted one function later. Retry mechanics at pipeline.py:305-354; min/mean/low aggregates at pipeline.py:523-533. external: Azure Document Intelligence / AWS Textract three-tier confidence routing; Sonix word-confidence heatmap toggle.
Rationale
This is the single richest signal the pipeline produces and it currently reaches zero users — every chunk looks equally authoritative. Practitioners consistently report that doc-level confidence hides local failures; a per-region lens answers "which parts do I double-check before citing this" at a glance. The adaptive retry is the most sophisticated thing the pipeline does and it is 100% invisible — showing the system noticing and fixing its own weak spots is a stronger trust story than claiming accuracy. Four of five ideation frames independently converged here.
Downsides
Making confidence public is a schema decision worth making deliberately (it becomes part of the API surface). Confidence must be threaded into chunk records (chunks don't carry it today), and coloring the markdown tab is costlier than coloring chunk cards because markdown renders as one blob. Confidence exists only for OCR'd regions — text-layer regions and demo mode show nothing, which the UI must communicate honestly.

Ghost Overlay — client-side page view with hover-synced regions

spatial-view Conf 85% Cx Medium
Description
A two-pane results view: the document pages on the left, chunks/markdown on the right. The twist that makes it affordable: render the PDF client-side (PDF.js) from the file the browser already uploaded, and draw the normalized 0–1000 bounding boxes — which every chunk record already carries to the client — as toggleable overlay layers colored by region label (title / paragraph / table / formula). Hovering a chunk highlights its source region; clicking a region jumps to its chunk. Zero server cost, zero pipeline change, no Modal spend.
Basis
direct: src/bumblebee/chunks.py:75-87 — every chunk carries "bboxes": [{"page": int, "bbox": [x1, y1, x2, y2]}] (normalized 0–1000 ints), shipped in the JSONL the client already holds and never rendered; page images are closed immediately after cropping (pipeline.py:203-204), so the server retains nothing — but the verifier confirmed the uploaded PDF is saved and available (web/bumblebee_studio/state.py:121-124). external: hover-synced source↔output panes are the headline interaction of the run-llama "baby-llamaParse" playground reference and the PDF-annotation click-a-region pattern; Mistral OCR 4 markets paragraph boxes + typed blocks as its flagship feature.
Rationale
This is the canonical "where did this text come from" trust interaction — the grounding/ citation pattern where trust is verified by clicking, not by reading a percentage. It turns the invisible layout-detection stage into the visual centerpiece and directly exercises the exact data (bboxes) the product sells to RAG builders. Five frames independently proposed a spatial view; this variant was selected because it needs no backend change at all.
Downsides
Largest frontend build of the five (PDF.js integration inside Reflex, overlay math, two-pane layout). Demo mode's hardcoded full-page bbox [0,0,1000,1000] renders as a full-page highlight — honest, but visibly less impressive than hosted parses. Very large PDFs cost client memory to render.
3

Parse Forensics — timing waterfall + cost receipt

pipeline-transparency Conf 90% Cx Small–Medium
Description
Replace the single "parse time" tile with two connected panels. (a) A stage waterfall: wait → read → render → layout → crop → OCR → format as horizontal bars, with queue-vs-exec splits — so a Modal cold start reads as "15 s queue wait, 2.1 s actual OCR" instead of apparent slowness. (b) An itemized cost receipt: tokens in/out × model rate = "$0.0042 for this parse · 0.4¢/page", with an optional comparison row against Azure Document Intelligence / AWS Textract / Mistral list prices per page.
Basis
direct: src/bumblebee/stats.py:100-110 — durations_seconds already records wait/read/render/layout/crop/ocr/format; models.py:145-166 (DocumentTimings) carries queue/exec splits; the API payload already returns tokens.{input,output,total}_tokens (api.py:81-85) which the UI fetches and silently drops (state.py:172-180 keeps only five tiles). external: the baby-llamaParse reference ships a live cost-estimate footer; browser-devtools waterfalls are the universally understood idiom for staged latency.
Rationale
Bumblebee sells itself on cost discipline yet the UI never states a price — the core pitch ("OCR only where it earns its keep") is static marketing copy instead of a live, per-document proof point. For the faculty audience, the waterfall doubles as evidence of engineering rigor and defensively explains cold starts. Verified as the cheapest high-value combination in the set: token data is already on the wire; timings need only a small api.py payload addition.
Downsides
Stage timings live in the batch pipeline's stats today, not the /v1/parse response — a small but real API payload change. Exposing wait reveals infra behavior (cold starts); decide whether that's public. Competitor price comparisons need sourcing and periodic upkeep.
4

Chunk Workbench — search, filters, section tree, re-chunk slider

chunk-structure Conf 85% Cx Medium
Description
Turn the read-only chunk grid into an instrument. Four affordances: (a) full-text search over chunks; (b) filters by kind / section / page; (c) expand-in-place past the 1,200-char display cap (the full text already sits in server state — lazy-fetch on click); (d) the standout: a re-chunk slider for chunk_max_tokens (128 / 256 / 512 / 1024) that rebuilds chunks instantly — chunks are derived purely from the layout JSON the client interaction already has server-side, so re-chunking needs no re-parse, no GPU, no network round-trip to Modal. A collapsible section tree (the chunker maintains a real heading stack that the UI currently flattens into a breadcrumb string) becomes the navigator.
Basis
direct: src/bumblebee/chunks.py:1-12 — "Chunks are derived purely from the per-page layout JSON that the formatter already produces… so they can be built anywhere that JSON exists"; chunk_max_tokens is already a parse-endpoint parameter (api.py:104-107); truncation at state.py:168 ([:1200]) with full text retained in _chunks_jsonl; heading stack at chunks.py:67-73, flattened at state.py:165. The chunks-tab dossier documents the absences: no search box, no filters, no expansion, no tree.
Rationale
The studio's target user is a RAG builder, and chunking granularity is the knob they care about most — letting them tune it live against a real document, then download the JSONL they shaped, is the difference between a demo and a tool. All of it is client/state-side work over data the backend already produces; the section hierarchy work is literally already done and then thrown away in a join().
Downsides
The re-chunk slider needs the chunker callable from the web state (import or small endpoint) and the layout JSON kept in session state for hosted parses. Search/filter over very large documents may need debouncing. Scope discipline required — this is four small features wearing one coat.
5

Instant Draft — race the engines + honest stage board

upload-progress Conf 75% Cx Medium
Description
Two moves against the blind wait. (a) Instant draft: on upload, immediately run the local text-layer engine (near-instant for born-digital PDFs) and show provisional results in ~1 s under a "draft — GPU parse running" banner; swap in the hosted results when they land. The draft-vs-final diff doubles as a live exhibit of what plain text extraction misses. (b) Honest stage board: replace the static "layout → OCR → chunks" label with a CI-style board (pending → running → done per stage) whose ETAs come from prior runs' stage timings scaled by page count — no streaming, no API change; full SSE progress is a deliberate v2.
Basis
direct: the two engines are one branch apart in web/bumblebee_studio/state.py:140-145 (if hosted_configured(): … hosted … else local), and run_parse is already a background Reflex event; the parsing label is a hardcoded constant (bumblebee_studio.py:139-151) in front of a single awaited JSON response with a 600 s timeout. external: CI dashboards (GitHub Actions / Buildkite) solved the identical "remote job, no signal until done" problem with expected-duration-from-previous-runs.
Rationale
A Modal cold start can mean 30–60 s of decorative spinner during the faculty demo — the single highest-friction moment in the product, and where live demos die. The race converts the product's built-in fallback engine into a perceived-performance feature using 100% existing code paths, and the stage board is honest without requiring the streaming rearchitecture.
Downsides
The local engine hard-fails on scanned PDFs — the race path must turn that into a silent skip (small change, but real). Draft-then-swap needs careful state design so results don't flicker or mislead. ETA priors are estimates and should render as estimates. Verifier rated this Medium-High confidence overall — the highest-uncertainty survivor.

Rejection Summary

#IdeaReason Rejected
1Session ledger / parse historyRefuted by verification: no persistence infra exists (reset_studio wipes all state); "seed of public benchmarks" jumps ahead of the deliberate private-until-benchmarks stage; low value for a single-document demo.
2Pixel-proof region cropsBasis overstated: base64 crops are discarded when OCR consumes them (RecognizedRegion has no image field) — real threading + payload-bloat cost, not "already built."
3Server-side page thumbnailsFights the existing page.image.close() lifecycle; the client-side Ghost Overlay (idea 2) delivers the same UX with zero server change.
4Blame gutter on markdownHidden rearchitecture: markdown renders as one rx.markdown blob; per-block hover mapping requires decomposing the renderer.
5Filmstrip document timelineSilently depends on retained page thumbnails (rejected above); revisit if idea 2 ships and demand appears.
6Full SSE/job streaming progressReal backend rearchitecture (single sync request today); the ETA-prior stage board in idea 5 captures most of the value — revisit when the API shape is decided.
7Actionable error diagnosticsSound but lowest wow-per-effort for a curated-input demo; failure phase already reaches the client (double-wrapped in strings). Good backlog polish.
8Evidence-pack HTML exportDerivative: its value depends on ideas 1–3 landing first; revisit as the take-home artifact after.
